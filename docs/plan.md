# 梦由心生工作台 — 产品方案

> 版本：M0 骨架（2026-11-22）。依据：调研报告（2026-11-22，拼法已敲定）+《工作台完善方案-2026-11-20》（现状诊断与业务规则）。
> 状态：方案已定，骨架先行；引擎与界面按第 11 节里程碑推进。

## 1. 目标与非目标

**目标**：一台 Windows 电脑、双击安装、本地运行的一人公司工作台。董事长（用户）定方向，CEO（总管 Agent）派活，7 个岗位 Agent 各干专家的活，8 步工单从选品走到复盘，全程留痕、关键节点等人点头。

**非目标**：

- 不做成云服务、不依赖任何云端数据库；飞书多维表格只是可选同步。
- 不做全自主无人值守：花钱、删数据、对外公开、发前审查，永远要人点头。
- 不抄任何一个现成项目：没有一个开源项目是“精选联盟 7 岗工作台”的现成答案，做法是按第 10 节拼起来。

## 2. 业务背景

抖音精选联盟达人带货赚佣金。**没有店铺、不进货、不囤货。** 选品只看四个维度：佣金率、销量、评分、退货率。选品 9 维标准尚未定（排最后），评分公式权重（佣金率 40 / 销量 30 / 评分 20 / 退货率 10）是助手起草的**示例权重，未经用户确认**，代码与界面里一律标“示例权重，未定”，不得当成定好的标准。淘汰规则同理：退货率高于 8%、评分低于 4.5 这两条未经用户确认，不作为默认规则；唯一已确认的淘汰线是**佣金率低于 20% 不推**。

## 3. 组织：董事长 + CEO + 7 岗

| 岗位 | 职责 | 铁律 | 验收（凭什么算干完） |
|---|---|---|---|
| 董事长（用户） | 战略、预算、拍板 | 不可逆事项先点头 | 审批记录 |
| CEO 蚕宝宝（总管） | 派活、校验、汇总 | 只派活、校验、汇总，不做专家活 | 工单流转记录 |
| 选品 | 从选品池挑商品 | 佣金率低于 20% 不推 | 商品进入“在推”状态 |
| 编导 | 写脚本；合规写进脚本里 | 极限词零出现、医疗功效零宣称；合规是编导的责任 | 脚本过禁词检查 + 人工复核 |
| 拍摄 | 按脚本拍摄 | 画质不达标重拍 | 画质评分达标 |
| 剪辑 | 剪辑、字幕、封面 | 字幕错字零容忍 | 错字 0 处、封面已做、时长核对 |
| 分发 | 多平台发布 | 每天至少发 1 条 | 发布记录（平台 + 视频 ID） |
| 投放 | 付费投放 | ROI 低于 1.5 立即停 | ROI 实时值、花钱审批记录 |
| 对帐 | 佣金登记与勾稽 | 每一笔佣金都留记录 | 今日佣金 = Σ已结算订单佣金，差异为 0 |

岗位配置见 `config/posts/*.jsonc`，格式为 CrewAI 式角色卡：role + goal + backstory + tools + guardrails。改功能改配置，不改代码。

## 4. 八步工单流转与守卫

```text
选品 → 编导 → 拍摄 → 剪辑 → 分发 → 投放 → 对帐 → 复盘
```

| 步骤 | 岗位 | 输入 | 输出 | 守卫（命中即打回上一岗） |
|---|---|---|---|---|
| 1 选品 | 选品 | 选品池 | 商品进入“在推” | 佣金率 < 20% 不得通过 |
| 2 编导 | 编导 | 商品 + 卖点 | 脚本正文 | 脚本命中禁词/极限词不得进拍摄 |
| 3 拍摄 | 拍摄 | 脚本 | 成片素材 | 画质不达标重拍 |
| 4 剪辑 | 剪辑 | 成片素材 | 30 秒成片 + 字幕 + 封面 | 字幕错字 > 0 打回 |
| 5 分发 | 分发 | 成片 | 各平台发布记录 | **发前审查未通过不得发布**（强制 HITL，见第 5 节） |
| 6 投放 | 投放 | 已发布视频 | 投放记录、ROI | ROI < 1.5 不得进投放，已在投的立即停 |
| 7 对帐 | 对帐 | 订单、佣金事件 | 对帐单 | 今日佣金 ≠ Σ已结算订单佣金时标红待核对 |
| 8 复盘 | CEO + 各岗 | 全单事件日志 | 复盘结论、下期改进 | 无守卫；结论写入日志 |

状态机表达：每份工单一个状态机（XState 与 LangGraph StateGraph 同构），阶段取值为选品/编导/拍摄/剪辑/分发/投放/对帐/复盘，状态取值为待开始/进行中/已完成/已阻塞。复盘不是一个岗位，不能按“哪个岗在干活”推导步骤——步骤一律以工单阶段字段为准（这是旧看板 D2 断点的教训）。

## 5. 人工审批（HITL）

以下事项必须停下来等人点头，审批留痕（`approvals` 表 + 事件日志）：

- 发前审查：验脸验声留证据（帧、转写文本、语速），审查通过才允许发布；任何 Agent 不得自行放行。
- 花钱：投放预算、充值、任何付费调用。
- 改规则：改禁词表、改选品标准、改评分权重、改守卫阈值。
- 对外公开：发布、对外发消息、公开分享。
- 删数据、批量改动。

审批形式：桌面端审批卡片（批准/打回/稍后）为主；飞书卡片审批为可选模块（借鉴 Agent-Autoloop 的 ask/notice/resolve/later 回执协议）。

## 6. 岗位配置格式

`config/posts/<post>.jsonc`，字段：

| 字段 | 说明 |
|---|---|
| id / name | 岗位标识与中文名 |
| stage | 对应 8 步中的第几步 |
| role | 一句话角色定位 |
| goal | 该岗要达成的目标 |
| backstory | 背景与边界：这个岗是什么、不许干什么 |
| tools | 该岗可用的工具名（注册表里须有实现，骨架阶段为占位） |
| guardrails | 硬规则列表：命中即打回或拒绝 |
| inputs / outputs | 输入与输出（与第 4 节流转表一致） |
| needs_approval | 该岗哪些动作须人工批准 |

`config/crew.jsonc` 定义整条流水线：8 步顺序、守卫、交接规则、熔断（跳数上限 8 层）与审批点。

## 7. 数据驱动 SOP（三层做法）

目前没有成熟开源产品能把历史工单直接喂进去就生成可执行工作流。可行做法分三层：

1. **流程发现（离线分析）**：工单/日志导出为事件日志（case_id=工单、activity=步骤、timestamp、执行人、结果），用 PM4Py 做流程发现与一致性检查。PM4Py 为 AGPL-3.0，**只作离线分析工具单独使用，输出结果再人工转 SOP，代码不并入本 MIT 项目**。
2. **LLM 起草**：用 LLM 总结高频路径、变体与瓶颈，起草 SOP 草稿（落到 AgentScope SOP / YAML 规则格式）。LLM 总结有幻觉风险，草稿必须经人验证。
3. **人工批准后落规则**：批准后的 SOP 转为可执行规则（Flow / LangGraph 节点 / 岗位配置），进入 `sop_rules` 表，状态为“已启用”；持续评估，不合格打回第 2 层。

前提：事件日志质量——case ID、时间戳、活动命名必须一致，否则第 1 层发现的是噪声。

## 8. 透明化设计

- 每个工单 = 一个 thread/run：状态机 + 事件日志（SQLite 只追加）+ checkpoint。
- 岗位详情页 = 该岗当前工单的“流程图（当前节点高亮）+ 步骤时间线 + 正在干什么（最后一条事件）+ 历史（全部事件 + 审批记录 + 证据链接）”。
- 实现路径：LangGraph checkpoint（SQLite）或自研事件溯源（Agent-Autoloop 式）+ 前端 React Flow 画流程图。不为“可见”单独引重型引擎。
- 宠物状态绑定真实工单状态（忙/闲/求助/完成），不做纯装饰动画。虚拟办公室为一屏可视化，可降级为 2D，绝不拖垮主流程。

## 9. 数据模型

见 `db/schema.sql`。表清单：商品（products）、订单（orders）、工单（work_orders）、日志（ops_logs）、事件（events）、审批（approvals）、每日数据（daily_stats）、岗位状态（post_states）、SOP 规则（sop_rules）、事件溯源（event_log，只追加）。

佣金模型（借鉴 Medusa 式做法）：订单归因不可变 + 佣金记账与分发分离；退货订单佣金冲回；今日佣金 = Σ当日已结算订单佣金，实时算、不存数；余额 = Σ已结算佣金 − Σ已提现。

字段命名教训（旧看板 D8c）：列名不用数字开头，`sales_30d` 而不是 `30d_sales`。

## 10. 部署方案

| 方案 | 结论 |
|---|---|
| **Tauri 2（首选）** | React 前端 + Rust 壳 + 系统 WebView2，.msi / NSIS 双击安装，安装包 3–15 MB；官方 SQLite 插件、密钥存 keychain。坑：离线安装需另加约 127 MB WebView2（Win10/11 多数已自带）；Python 后端须作 sidecar 打包。 |
| Electron（备选） | 生态最熟、Node 后端可直接复用；安装包 80–200 MB，内存 150–400 MB。 |
| Docker（可选） | 仅留 `docker-compose.yml` 给进阶用户，不作主方案。 |
| 纯 Web localhost（过渡） | 先以 localhost Web 服务 + 浏览器跑通，再包 Tauri。 |

模型调用走 OpenAI 兼容 API，Key 由用户在设置页自填，存系统 keychain，不进代码与仓库。飞书同步与飞书卡片审批作可选模块。

## 11. 里程碑

- **M0 骨架（本次）**：目录、岗位配置、数据库、CI、产品方案。完成标准：仓库结构完整、配置与 schema 可校验、CI 能跑。
- **M1 派活引擎**：rules.json 声明式派活、单一派活入口、事件溯源（SQLite 只追加）、认领与显式交接、8 层熔断、指令数据分离。完成标准：一条工单能从选品自动走到复盘，事件日志完整。
- **M2 审批与可视化**：桌面审批卡片、发前审查节点、岗位详情页（流程图 + 时间线 + 证据）、工单看板拖拽、虚拟办公室一屏。完成标准：点开岗位能看到真实流程与历史。
- **M3 喂数据 SOP**：事件日志导出、PM4Py 离线发现、LLM 起草 SOP、人批后落规则。完成标准：用真实历史工单跑通一轮三层流程。
- **M4 发布**：.msi 安装包、首次启动向导（填 Key、选数据目录）、飞书同步可选模块、用户手册。完成标准：在用户 Windows 电脑上双击安装可用。

## 13. 风险与未验证项

- 抖音精选联盟 API 的可用性与合规边界本次未调研，须另行确认；分发与数据读取现阶段走浏览器登录态（扫码登录一次，会话存本机）。
- 飞书卡片在真实账号上的端到端审批未验证（Agent-Autoloop 自述仅跑通发送/按钮回调/卡片更新）。
- 各候选在用户机器（i5-13490F / 32GB / RTX 4060、Windows）上的实测安装与性能未验证；M4 发布前须在真机上装一遍。
- Agent-Autoloop 仅 19 天历史（2026-11-03 创建），规则/协议格式可能变动；引用其设计时以本仓库内的实现为准，不盲从上游。
- 选品 9 维标准、禁词表内容、投放口径、对帐口径仍待用户定；规则未定之前不建 POST 流转引擎（旧方案“先 A 后 C”的结论仍然有效）。
